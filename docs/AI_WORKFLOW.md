# AI 工作流程与评估

## 实现范围

规则扫描使用 axe-core 和受控 Chromium，属于确定性工具，不称为大模型检测。语义辅助复核根据最多 20 个候选元素的名称、角色和附近文本提示疑点。系统依据元素类型检索 WCAG 摘要，与页面证据一起交给模型，并在结果中保存关联来源。用户需要先同意发送这些内容，并对结果及来源适用性作人工判断。模型输出格式或编号无效时最多纠正一次，仍失败则不保存结果。没有疑点不代表页面符合 WCAG。

「AI 分析与修复」对普通文本问题通过 OpenAI 兼容的工具调用协议，让模型选择调用以下工具：

1. `inspect_issue` 返回服务端绑定的当前问题、操作类型及有限的局部上下文；模型不能选择其他文件或问题。
2. `search_wcag` 在本地 WCAG 2.2 中文摘要中按问题类型和关键词检索，返回最多三条摘要与 W3C 原文链接。

模型必须调用这两个工具并给出受限 JSON；源码 Agent 在提出可验证的计划前，还必须调用源码与浏览器证据工具。服务端校验工具名、参数、次数、返回结构和补丁类型；验证失败可反馈给模型并受限重试。检索先依据检测规则约束相关 WCAG 成功准则，再用中英文词项 BM25 排序；它不使用向量检索。素材是团队整理的中文摘要，不是规范原文。链接和摘要需要结合原文核验，检索结果不保证全部适用。模型无法判断图片或控件的真实用途时应拒绝猜测；图片与图标按钮由通用视觉服务分析，发送经大小限制和验证的本地快照图像。图像观察与用途推断分开，视觉服务的建议不作为确定性 WCAG 违规或复测结果。

源码 Agent 可以调用 `validate_candidate`，在读取所需证据后主动验证候选方案，获得自动检查摘要或失败原因，并据此调整。服务端最多进行三次候选验证，对已经通过的同一计划复用检查结果。模型未主动调用时，最终计划仍会经过相同验证，用户仍需审核。Agent 的自主验证以工具调用和检查记录为依据，不代表验证了真实网站的全部动态功能。

用户选择 AI 分析时，表单和链接若缺少足够明确的用途证据，系统会将受限的浏览器语境交给模型，并通过工具读取问题及检索规范。模型的名称仅作为待确认建议，不直接生成补丁；模型无法判断或不可用时需要用户填写。明确证据仍可通过规则生成建议。修复界面展示该次模型请求次数、可获得的 token 用量和检查过程，视觉分析与语义复核当前尚未统一记录用量。

模型生成的建议只创建待审核补丁。用户确认后才修改本地副本，系统检查文件哈希、目标、结构并重新扫描；未通过验证则保留原版本。工具过程和检索来源保存在验证记录和 JSON 导出中。该机制不能保证网页的动态功能或实际无障碍体验，需要人工、键盘和屏幕阅读器测试。

## 图片与图标的证据和隐私

图标按钮的视觉分析结合元素附近的截图、局部文本与语义；源码 Agent 在视觉服务已配置且目标含图标时必须调用视觉工具，证据不足时不会通过候选验证，用户可以填写实际用途。视觉服务不可用或响应无效时转为人工处理，不自动猜测。图片用途分析后按内容性、装饰性或不确定的语境检索相关摘要，仍需用户确认用途。视觉截图中的信息及模型推断不等同于按钮真实功能。

文本模型、视觉模型和语义辅助复核发送的页面文本会尝试遮蔽邮箱、中国大陆手机号和常见凭据格式，模型输出中的遮蔽占位符不会直接用于修复值。这是有限的规则过滤，不能识别所有隐私信息；发送的图片像素不会自动遮蔽，使用者应先确认图像及截图内容适合发送到所配置的模型服务。工具结果来自网页时被视作不可信数据；工具只读取受限的当前项目证据，补丁由服务端验证和用户审核。

## 比赛验证建议

内置的 `evaluation/wcag/cases.json` 是团队编写的 16 个小样本，含 15 个规则及 1 个不支持规则的拒答测试。`npm run eval:wcag` 比较原有九条摘要和词项匹配，与当前规则约束 + BM25 的 Top-1/Top-3 条款命中；`npm run eval:wcag -- --live --output evaluation/wcag/results-local.json` 还会对其中 5 个问题分别调用真实模型，比较不提供检索内容和提供检索摘要时的答案。输出包含答案、条款、耗时和 token 用量，不保存密钥。实际调用会消耗模型额度。

这些题目、规则映射与标准答案均由同一团队维护，属于开发集上的功能检查，不是独立泛化评估；Top-1/Top-3 把不支持规则的正确拒答也计为通过。生成评估仅检查答案中的指定词项及条款编号，不等同于完整语义正确率。单次对比不能证明检索必然提升生成质量，应保留原始记录并由人工核对回答、规范适用性和失败案例。[示例结果](../evaluation/wcag/results-2026-11-09.json)记录了一次真实模型运行，模型、时间、逐题答案及分数以结果文件为准。

`npm run eval:repair-rag` 检查八个人工编写的修复场景及其检索来源；加 `-- --live --output /tmp/repair-rag-results.json` 使用相同模型和页面证据分别生成有无检索的建议，并保留逐题输出、耗时和人工审核字段。实际调用会消耗模型额度。条款匹配不能代表建议正确，需要人工检查案例列出的要求；这些文本场景不等于实际视觉模型评估，也不是独立盲测。

[2026-11-10 真实模型对比记录](../evaluation/wcag/repair-results-2026-11-10.json)使用 DeepSeek Flash 完成 8 组、16 次调用。含正确拒答在内，无检索和有检索的预期条款格式匹配分别为 7/8 和 8/8；语义及规范适用性尚未人工评分，不能据此断言检索显著提升修复质量。

该次运行使用 DeepSeek Flash：16 个检索案例中，原方案 Top-1 为 8/16、Top-3 为 11/16；当前方案均为 16/16。5 个生成问题的自动粗评中，有无检索均为 5/5，因此这组数据**没有证明**检索提高了回答正确率。该结果主要验证条款映射和调用流程，不应外推到真实网页或未见过的规则。

进一步准备与开发样例分开的授权测试页面，覆盖明确标签、语义含糊的按钮、缺少图片说明、颜色对比度以及模型无法判断的反例。每个案例记录页面、问题类型、预期结果和人工标注。

在相同案例上分别记录人工建议、直接 AI 建议和 AI 检索分析的结果：

- 建议是否可解析、语义是否准确、是否正确拒绝无依据的猜测；
- 检索来源是否真实且适用于该问题，人工确认使用的条款；
- 用户批准后目标问题是否消失，有无新增自动检测问题或语义错误；
- 各阶段用时、失败次数和模型服务费用。

记录样本数、模型名称、运行日期和人工评价标准，保留失败案例。现有模拟模型测试只验证流程与安全限制，不是对真实模型的效果评估；规则引擎的检测基准也不能作为 AI 效果数据。
